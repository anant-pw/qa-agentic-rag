## 3. Findings

### 3.1 Where the time goes (new Ollama timing fields)

| | phi4:14b | llama3.1:8b |
|---|---|---|
| Prompt size | ~2,000–2,500 tokens | same |
| Reading the prompt | 128–373 s | 29–78 s |
| Writing speed | **0.05–1.2 tokens/s** | ~4 tokens/s |
| Semantic answer, end to end | 101–1,387 s | 12–164 s |

- **Reading the prompt dominates a new question.** On an identical repeated prompt, Ollama's prefix cache cut prompt reading from 373 s to 5 s.
- **phi4's writing speed varies about 25× between answers.** For example, one answer wrote 42 tokens in 912 s. That is swapping, not the model's normal speed.

### 3.2 The machine is out of RAM with phi4:14b loaded

- **Host memory:** 0.1–0.5 GB free throughout.
- **Ollama:** `llama-server` held 7.2–7.5 GB resident, but phi4:14b is 9.05 GB. So part of the model was being paged in from disk during generation.
- **Side effects on other services:**
  - OpenSearch logged garbage-collection pauses of 1–6.6 s on tiny 9 MB collections, at both 256m and 512m heap.
  - Three requests failed on infrastructure timeouts, never on the model:
    - 2× OpenSearch read timeout (10 s)
    - 1× Ollama embedding timeout (30 s)

  All three happened with phi4 loaded. There were none in the llama3.1:8b run.

### 3.3 Why the heap reduction was reverted

At 256m the heap was only ~44% used. The GC pauses came from the JVM's memory being swapped out, not from a full heap, and a smaller heap means more frequent collections. The first eval run hit a 500 error (an OpenSearch timeout) at 256m. The same failure later happened at 512m too, so heap size is not the root cause. But 256m saved only ~256 MB and bought nothing measurable, so it went back to the known-good value.

### llama3.1:8b failures, read by hand

- **Q1** (expected result of the test case cited by BUG-1001). Neither model had TC-0142 in its retrieved top 5; context held BUG-1001, 1024, 1002, 2030, 2095. Both models answered "account should unlock after a cooldown", which is a thin, partly inferred answer. The actual TC-0142 expected result is richer: locked after 3 failures, a clear lockout message, and success after a 5-minute cooldown. phi4 passed only because it also named TC-0142. **This is a retrieval gap on the 173-doc corpus (weakness W1), not a model difference.**
- **Q9** (ERR_403_FORBIDDEN aggregation). llama listed 3 of the 5 documents and omitted BUG-1012 and BUG-1019, even though both were in its context. The duplicate relationships it did state (2042→2085, 2085→2099) are correct per `document_references`. phi4 listed all 5. **This is a real completeness weakness of the 8B model on multi-document aggregation.**

The Phase 6 reason for disqualifying llama3.1:8b (miscounting a structured_filter question) no longer applies on `/generate/agentic`. Both count questions go through the deterministic route, and both passed.

## 5. Recommendation (decision for the project owner)

- **Keep field lookup on.** It takes the 4 single_doc_factual questions from minutes to under 1 s, with verbatim answers.
- **Model choice is a real trade-off. Nothing was switched.** `.env` still says phi4:14b, and the container runs phi4:14b.
  - **phi4:14b:** best correctness (0 FAIL), but unusable latency on this 16GB machine: median ~7.7 min, max 23 min. It also destabilises OpenSearch and embedding (1 of 20 requests errored).
  - **llama3.1:8b:** 6× faster (median 74 s), no infrastructure errors, but 1 real aggregation miss (Q9).
  - **Possible middle ground (untested):** llama3.1:8b for demos, plus a prompt or deterministic fix for error-code aggregation. Error-code → document is already a table (`document_error_codes`), so "which bugs have ERR_X" could become a third deterministic route, just like counts.
- **Next evidence to gather:**
  1. A Tier B hand-grade of llama's 11 LLM answers (`eval/runs/2026-10-01_llama3.1-8b/run_eval_generation_results.json`).
  2. Fix the TC-0142 retrieval gap: for a resolved ID, pull its referenced documents into context.

## 8. Follow-up (same day): error-code route, reference expansion, data bug

### 8.1 Error-code route (`DETERMINISTIC_ERROR_CODE_LOOKUP`, default true)
`app/generation/error_code_lookup.py`. When a question names one ERR_* code and asks "which bugs/documents …", the answer comes from `document_error_codes`, with no LLM call. The "are they related?" half is answered only from recorded `document_references` among the matched documents, plus an explicit note that a shared error code is not evidence of a shared root cause.
- Offline trigger test: 10/10 correct. Why/how-many/fix/steps questions and questions naming two codes all fall through to the semantic path.
- End to end: ERR_401_UNAUTH listed 3/3 documents and ERR_403_FORBIDDEN listed 5/5, each with its recorded duplicate rows. This fixes llama3.1:8b's Q9 miss by construction; it removes the model from that question.

### 8.2 Reference expansion (`REFERENCE_EXPANSION`, default true)
When a question names an existing ID, up to 3 documents it references are placed right after it in context, in priority order: cited test case, then duplicates, then related (`fetch_reference_targets()` in `context.py`, `_expand_references()` in the router).
- Q1 context before: BUG-1001, 1024, 1002, 2030, 2095 (no TC-0142). After: **BUG-1001, TC-0142**, 1024, 1002, 2030.
- phi4:14b on Q1/Q2: **2/2 PASS** (243 s, 440 s). Both answers now state TC-0142's actual expected result (lockout message, 5-minute cooldown). Before, the answer was only "unlock after cooldown" (`eval/runs/2026-10-01_phi4-14b_refexp/`).

`routing_check.py`: **22/22** (new rows: ERR-agg, ERR-agg-seed, CTRL-errcode-why, REF-expand).

### 8.3 Data bug: module/status swapped on all 120 synthetic bug reports
- **Symptom:** synthetic bugs had values like `module=Resolved, status=API`.
- **Cause:** `scripts/generate_synthetic_data.py` appended rows with hardcoded `fieldnames=[..., "module", "status", ...]` under an existing header ordered `status,module`.
- **Impact:** `module` and `status` filters, and therefore count answers, silently excluded every synthetic bug. `check_structured_filter` compares against the same database, so the eval could not detect it.
- **Done:**
  - The generator now appends using the existing header.
  - `data/bug_reports.csv` is fixed. The backup is `data/bug_reports.csv.bak-2026-10-01`. Verified: the 25 original rows are identical, and the 120 synthetic rows differ only by the swap.
- **Still to do (needs owner to run; the Postgres write was not permitted from the session):**
  ```bash
  docker exec rag-postgres psql -U rag_user -d rag_db -c "UPDATE documents SET module = status, status = module WHERE doc_type='bug_report' AND external_id ~ '^BUG-2';"
  python -m scripts.build_index          # new index + alias swap; previous index kept
  ```
  The `UPDATE` reverses itself if run a second time. Embeddings do not include module or status, so vectors and the 0.75 guardrail threshold are unaffected. Counts will change; for example, Open bugs in Login go from 4 to 8.
